# Onboarding / root loading fix

## Findings and root-cause limits

The inspected code had no guard that waited for `members.length === 2`. `onboardingStep()` collapsed every existing duo into `ready`; the protected layout admitted a one-member duo into demo providers without any real pairing status. Meanwhile the root `app/loading.tsx` wrapped the asynchronous account/layout resolution in the generic “Getting your duo ready…” Suspense fallback. That text was a route-loading fallback, not a deliberate pairing state.

With the real Account A session, the previous layout was temporarily restored for a comparison test: it reached the demo dashboard, so the reported **indefinite** hang was not consistently reproduced. We cannot honestly identify its original runtime trigger as a nonexistent two-member guard. The fix addresses the confirmed state-model gap and removes the account-resolution work from that broad loading boundary. No database changes or auth bypass were used.

## Changes

- `lib/auth/domain.ts`: explicit `profile`, `duo`, `waiting`, `ready` states.
- `lib/auth/session.ts`, `lib/repositories/adapters.ts`: reject malformed membership responses rather than treating them as readiness; still verify the Auth user and read through RLS.
- `app/(app)/layout.tsx`: render the existing AuthFrame/PairingState for one-member duos, before initializing mock feature providers. Existing two-member app composition is unchanged.
- `app/loading.tsx` moved to `app/(app)/loading.tsx`: page loading occurs inside the resolved protected layout; wording is “Loading DuoPet…”.
- `app/onboarding/page.tsx`, `components/auth/Onboarding.tsx`: stable waiting title/status, copy invite with clipboard-failure fallback, existing authoritative refresh, and app entry only once paired. No fake membership or polling.
- `lib/auth/confirmation.ts`, `app/auth/confirm/route.ts`: explicit supported link shapes, safe expired/PKCE/unavailable outcomes; no tokens or raw errors in diagnostic logs.
- `lib/auth/actions.ts`, `components/auth/ConfirmationRecovery.tsx`, `components/auth/AuthForm.tsx`, `app/login/page.tsx`, `app/signup/page.tsx`: actionable confirmation guidance and an explicit resend form with pending/error/status feedback and existing Supabase rate limits.
- `backend.test.cjs`, `README.md`, this report: regression tests, exact template/settings and validation results.

Next.js dev also generated its standard `AGENTS.md`/`CLAUDE.md` guidance files. Schema, RLS, goal providers and timezone utilities were not changed.

## Expected transitions

| Authenticated account state | Result |
| --- | --- |
| Profile missing or display name incomplete | `/onboarding`: profile setup |
| Completed profile, no duo | `/onboarding`: Create Duo / Join Duo |
| Duo with current user only | Root/protected routes and onboarding show **Waiting for your duo · 1 of 2 members**; invite code, copy, Check pairing, Sign out |
| Duo with two members | Root renders normal app; onboarding shows **Your duo is complete 🐾** and Enter DuoPet |
| Malformed duo response or server failure | Error boundary, not a fabricated partner or readiness state |
| Signed out | Login; existing verified-user and RLS checks remain |

Check pairing uses `router.refresh()` and reloads server account data. While the one-member account waits, the existing demo dashboard is intentionally unavailable. Theme support, existing AuthFrame styling and local/duo timezone rules are preserved.

## Confirmation findings

The previous handler already supported both `?code=...` and `?token_hash=...&type=email`. The new handler additionally accepts signup token hashes and categorizes recoverable errors. Recovery/passwordless token types and ambiguous mixed links are rejected.

A `code` URL is a valid PKCE callback, normally generated by Supabase's verification endpoint when using its default ConfirmationURL email template. Exchange requires the original verifier cookie and the same browser/origin. A code in logs alone does not prove a template mismatch. `otp_expired` can mean an expired, invalid, or already-consumed link; it does not reveal which without the original Auth logs/link lifecycle.

Both supplied accounts signed in successfully. The hosted public Auth settings reported `mailer_autoconfirm=false`, so email confirmation remains enabled and both accounts are already confirmed. This is consistent with email verification succeeding before a later callback or repeat-link failure. We did not reuse old links or disable confirmation.

Required recommended template and redirect settings are in README. Prefer the direct `TokenHash` email template for this SSR app; retain code support for existing PKCE emails. Use newly sent links after template changes. Already-confirmed users should sign in; unconfirmed users can request a new confirmation email through Login. Resending is user-triggered and returns non-enumerating feedback.
